## 5. ⚠️ 审阅闸门缺口（测试暴露，**待用户拍板是否登记 M24**）

时序实证：06:51 渠道会话跑批写 review 范围锁 → 06:59 阶段 1 推送**失败**（M17，
`.review-pending` **从未写入**）→ 07:30 cron 启动时**重写自己的 broadcast 锁**（发起方
声明语义，覆盖 review 锁），此时既无待审标记也无 .pushed → **全量推送放行，钉钉收到
日报**（rc=0，产物校验通过）。

缺口本质：**审阅闸门的保护依赖"阶段 1 推送成功"留下 .review-pending；投递失败静默降级
成普通全量日**。候选修法（二选一或并用）：
① 阶段 1 推送失败时也写 `.review-pending`（标注"投递失败待重试"），使当日 cron 的
broadcast 被挡；② `run_scan.sh` 写 broadcast 锁前检查当日是否已有 review 锁/待审标记，
有则拒绝覆盖（需显式 `push_scope.py --clear` 才能接管）。

## §13 · 抽取段性能事故（2026-11-18）：45 分钟那轮的真因与修法

**触发**：用户问"今早的检索为什么这么长时间发布"。晨间跑批 07:30:01 → 08:14:55
共 45 分钟，其中确定性加工段 36 分 45 秒（81%），取数段只 7 分 45 秒。

**根因三层**（证据见 known-issues M26，完整数据表在那儿）：

1. **全局模型被换**（2026-11-16）：`~/.hermes/config.yaml` 的 `model.default`
   从 `MiniMax-M2.5` 改成 `MiniMax-M3.1-Flash`。当天生产零部署 → 非代码回归；
   仓库里 grep 不到任何切换记录 → 改的是全局配置且没留痕。
2. **新模型行为变了**：干净单轮 7.9s → 18.3s；且 **22% 的调用脱离"单轮"契约**
   跑成 Agent 工具循环（均 70.7s，最长 257.6s），模型自己去读仓库文件、查生产库
   `epidemic.db`、`web_extract` 抓外网 —— **数据面拿到了执行面**。
3. **结构性根因：用错了工具层级**。抽取只需要"一次确定性文本补全"，却用 Agent
   CLI 跑，每份白付：注入整个仓库上下文（实测 74 次调用 `in=1,043,779` token，
   我们自己发的 prompt 只占 89,600 —— **91% 是注入**）+ CLI 启动 ~5s + 全套工具 +
   `max_turns: 50` + 折合 171 万 token/日。

**量只是放大器**：存档 12 份（11-08）→ 64 份（11-18，WTO 附件 40，尼加拉瓜一家
27），串行线性叠加。

**修法（已落地，本地自测全绿）**：

| 层 | 改动 | 文件 |
|---|---|---|
| 调用层 | 抽取改**直连 Anthropic 兼容端点**（无工具/无 CLI 启动/无上下文注入） | `scripts/extract_records.py` |
| 模型 | `EXTRACT_MODEL` 钉死 **M3.1-Flash**（用户拍板 M2.5 退场；M3.1 的冗长靠 max_tokens+提示加固+重试加预算三道防线压住） | 同上 |
| 并发 | 6 路（worker 只调用+校验，主线程按完成顺序落盘 → 崩了不丢已完成部分） | 同上 |
| token | `max_tokens=8000` + prompt 输出格式硬约束 + **失败重试加预算(×2)**（该端点**思考 token 也吃输出预算**，实测 thinking≈800~1100；`thinking` 参数实测不支持） | 同上 |
| 兜底 | CLI 通道保留但强制 `--safe-mode` + 显式 `-m`（**去掉 `--yolo` 不管用**） | 同上 |
| 账目 | 抽取自记 `data/raw/<日期>/extract-usage.json`，预算侧合并（否则预算闸门瞎） | `extract_records.py` + `token_budget.py` |
| 调度 | `push_scope.py --refresh`：只有当日日报已生成才刷新锁声明时刻 | `push_scope.py` + `run_scan.sh` |
| **key 传递** | **key 必须真的进到 python 子进程**：`run_scan.sh` 普通 `source`（无 `set -a`）不导出给子进程 → 显式 `export "$EXTRACT_API_KEY_ENV"` + `extract_records._load_api_key()` 从 `~/.hermes/.env` 补载（双保险） | `extract_records.py` + `run_scan.sh` |

**上线当场发现并修掉的坑（2026-11-18）**：部署完现场复核才发现 ⑩ —— `run_scan.sh`
用**普通 `source`**（没带 `set -a`）加载 `~/.hermes/.env`，变量只是 shell 变量，
**传不进 `python3` 子进程**（生产实测：source 后当前 shell 里 `MINIMAX_CN_API_KEY`
有值、长度 125，子进程 `os.environ` 里查不到，`set -a` 才看得到）。后果是直连通道
拿不到 key → **静默回落 CLI 兜底**（刚淘汰的慢路径）→ 改造上了生产却一点没生效，
且日志上看不出来。**不修这次上线等于白上。** 同一个坑 `fetch_eping` 在 2026-10-31
已经踩过一遍（「挂接点检查到 key，python 却拿不到」），差点重犯。
顺带修掉 `~/.hermes/.env` 第 493 行 `EURLEX_WS_PASSWORD` 值末尾多出的一个反引号
（未闭合的命令替换把后面几行一起吞掉 → bash source 后 `EURLEX_WS_USER/PASSWORD`
实际缺失；备份 `~/.hermes/.env.bak-fix-backtick-20261118T100417Z`）。
**纪律：改完 `~/.hermes/.env` 一律 `bash -c '. ~/.hermes/.env; echo $?'` 验语法。**

**预期收益**：加工段 36 分 45 秒 → **约 1~2 分钟**；抽取 token/日 171 万 → 约
13 万（8%）；工具循环率 22% → 0；抽取段权限面 → 无。

**回滚**：`EXTRACT_BACKEND=cli` + `EXTRACT_WORKERS=1`，只改环境变量秒级退回。
